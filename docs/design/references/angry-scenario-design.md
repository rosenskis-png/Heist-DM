# The Angry GM's scenario design: reading notes

Notes taken chapter by chapter from The Angry GM's *True Scenario Designery* series and its supplements, and his *Let's Build a Pretty Good Dungeon* series (theangrygm.com, read 2026-11-05). They are a source for `docs/design/encounter-craft.md`, not the design itself: where they disagree with that guide or the decision log, those win. Bracketed notes are the reader's, about this game.

## 02 Just Design a Good Game
- Game Design Über Alles: every choice judged first by "what's the best gameplay experience"; gameplay can veto realism/story; "you can always find another way."
- World "levels with" players: overpowered threats exist but are telegraphed, located, never tripped over; choosing to engage them is deliberate, under no pressure. Escape encounters are built with a clear achievable goal and time to recognize danger.
- Encounter must clearly convey what's expected: the goal. If it looks winnable by violence but isn't, the game must scream it.
- Bad advice: "encourage failure for story" — players aiming to fail breaks the game.
- In-world justifications (why villain doesn't just assassinate) are excuses; real answer = so the game doesn't suck.
- Know medium limits: D&D not built for "we must run" (action economy, telegraphing, chase). TTRPG stakes are high vs videogames (Dark Souls respawn) — character death possible but one mistake shouldn't be death.
- Four reasons: game design encompasses narrative/immersion/exploration motives (sugar cake); open worlds become games anyway (players pick goal -> you add obstacles); games smooth social friction via focused constrained shared goals; lots of resources to learn.
- Real game design for GMs = building content (encounters/adventures), not mechanics. "D&D is an engine; the game is what you run."
## 03 What Is Scenario Design
- Three roles: System Designer (engine + components), Scenario Designer (in between), Game Master (renders world = "graphics + controller", resolves actions, does error handling & on-the-fly consistent content generation, steers back without saying no).
- Assemble-on-the-fly is reactive, can't see ahead → can't apply holistic top-down design. Scenario Designer can (e.g. Setup-and-Payoff: build both ends at once, tell GM).
- Minimal scenario design = Shortlisting; encounter tables are shortlists.
- Hats: patching a rule hole ≠ System Design; GM improvising ≠ Scenario Design. Other hats: World Design, Narrative Design, Component Design — they *serve* Game Design. Game Design has veto; World/Narrative don't. Resolve conflicts by bending the fiction (swamp ogre → add bog / reskin / backstory via environmental storytelling).
- High-stakes encounters (overpowered threat) need: lots of info, enough time to reach conclusion, several ways to recover from a bad choice before permanent loss. Else players turtle ("porcelain dolls").
- Scenario = whatever Scenario Designer hands GM. TTRPG isn't a game until GM runs it; GM always finishes an incomplete game. SD hands the "Completest" game possible; how complete depends on predictability — a known fight needs only stats; a faction/NPC-driven situation where approach is unknown needs tools for every approach. Perfect session = whatever players try, GM already has the right tool in front of them.
- [OUR GAME: AI DM = Game Master; encounter packet = Scenario. The completeness principle maps directly to packet content.]
## 04 Designing on Purpose
- Purpose-Driven Design: identify the gameplay need, then build something that fills it *in-fiction*. Players must be able to assess success/failure/progress → build grading in.
- Oona (Silverpine Watch): escort NPC asks players their mystery theory at the end; 3 graded responses (makes sense / missing something / don't buy it) without ever confirming truth. Fits her character + world sim. Same device mid-scenario = margin for error ("are you sure you didn't miss something?") → difficulty knob. [OUR GAME: companions as graders/checkpoints — huge fit.]
- Perpetual Adventure: players can retry forever because no firm failure state or don't know they failed (stab suspects until ghost vanishes). Fix with a deadline-shaped constraint — but specific to the scenario.
- Don't mistake mechanics for purposes: Ticking Time Bomb in every adventure / 4e Skill Challenges = one-size-fits-all hamfisting. Good general tools (Tension Pool, Blades Clocks) solve common problems without over-constraining. Solve *this* problem in *this* scenario.
- Design Statement (minimum, no more): Starting Point, Goal, Outcomes (plural, good and ill), ≥1 Challenge (usually biggest). Example dragon/village statement. Applies at every scale — encounter to campaign. Every element has an (often unstated) design statement: "why is this here?" + "is this good gameplay?"
- Über Alles ≠ Vor Allem: game design counts most, doesn't have to come first. Purposes: Tentpole (cool thing), Goal (needed by larger structure — e.g. heist: getting through the baron's back door), Narrative/Fantasy (theme, world plausibility), Gameplay (mode of play, gameplay need). Any purpose okay, but must *improve* gameplay — "doesn't make it worse" doesn't count.
- Encounters needn't advance plot but must serve a gameplay purpose (resource attrition in D&D).
- Economize: multi-purpose elements beat many single-purpose ones (Oona: goal, exposition, tutorial, grading, fantasy). Don't overdo — one villager doing everything kills the feel of exploring a village.
- Can't fill a gameplay hole → scrap the scenario. Element serving no gameplay purpose → cut (can exist off-camera). Double standard: a tentpole that fails gameplay must go; a pure-gameplay filler (rat fight) may stay. Labyrinths don't work at the table.
- No checklists/formulas.
## 05 Anatomy of a Game
- Encounter/adventure/campaign/game/scenario are the same thing at different scales.
- You ain't an engine designer: if you need rules that don't exist, you have a bad scenario, not a bad system.
- Game = Goals + Rules + Challenge + Context. Design statement covers them implicitly (rules/system implied; start + outcomes narrow context).
- Goal: in-game, tangible; "To win, the players must…". Every scenario at every scale has ≥1 explicit in-game goal. Not Motivation (fun, story; character desires are contextual reasons), not Reward (XP, loot). Goals come from the game. Player-chosen goals are possible but "drop them in the world and do whatever" isn't. Player Agency = Santa Claus.
- Rules incl. unwritten: Declare-Determine-Describe. Players know only what characters perceive; act only via individual character actions (no sky-god army control unless system has a rule; no cutscenes — put villain-evil info where characters perceive it).
- Rules Preprocessing: predict likely player actions (locked door: bash, pick) and hand GM skills, DCs, success/fail/crit outcomes. GM judgment is for what you failed to foresee. Crucially: listing predicted actions ≠ defining allowed actions (4e Skill Challenges' sin was presenting lists of possible interactions).
- Challenge: anything players must accomplish/overcome on the way to the goal, requiring any effort/skill + any uncertainty. ≠ Challenging/Difficulty. Rolling dice "technically" isn't a challenge. CR/DC aren't challenge. TTRPGs essentially only test choices — right/best/good choice in a situation → implies wrong/worse/bad choices must exist. Locked Door homework: what makes a door in-and-of-itself a challenge?
- Context: framework by which players understand goals and challenges; optional in baseball/Century, *vital* in TTRPGs: fiction informs calculus (orcs not charmable; consumables scarce) and opens infinite options (chop tree → ram). Goals, challenges and actions must be comprehensible both as world-sim and as unfolding narrative.
## 06 What Makes a Challenge  [CORE]
- Challenge (noun) = gameplay element players strive against toward the goal. Can be a construct (monster, trap), a situation (hostage, mystery), or a dynamic (resource management). Players, not characters, are challenged; characters are tools.
- Decouple: Challenge (the thing) / Difficulty (how much player effort/skill/risk) / Probability (dice odds). CR & DC are Probability, not Difficulty. No difficulty floor for something to be a Challenge.
- Macrochallenge: protracted, emergent challenge arising from several challenges/dynamics, never confronted directly (3 fights + boss = resource management across the whole; items/info found along the way help vs boss). Distinguishes adventures from obstacle courses.
- TTRPGs test only mental abilities, essentially *choices*: (a) "what approach do you take to this situation?" (b) "how do you prepare for challenges ahead?" Tests tactics, resource mgmt, deduction, prediction, memory/recall, risk mitigation.
- Meaningful Challenge: options substantially different in outcome, AND different players would choose differently. Everyone picks the same → Meaningless (pick higher damage). Not every challenge must be meaningful — vary it; simple locked doors are fine.
- Locked door in default D&D: pick vs bash is a Calculation (better odds), no costs/risks, retry free → meaningless; that's the system, the scenario must add meat.
- Meat that differentiates: Obfuscation & Deduction; Costs & Consequences (difference in *kind* not amount — pick = time, bash = noise); Incomplete Information (unknown beyond door; bash = surprise if works / alert if fails, pick = stealthy) — but zero info = random choice, and hiding DCs doesn't make it incomplete-info; Incomparables (apples vs suspension bridges); Dilemmas (sacrifice one desire for another; trolley problem is a Calculation). Real challenges mix these; some meat comes from system (spell slots), some from scenario (nearby monsters, wandering tables). Don't build by checklist.
- Creativity tests suck: open-ended "here's a problem, solve it" (washed-out bridge) → dead stop, blank stares, "can I Swim check?". Players aren't genius problem-solvers but *think* they are; the sense of agency comes from *figuring things out*, not real freedom. Scenario must be playable even if players produce nothing clever. Leave door open for creative solutions (GM handles them; best designers anticipate obvious None-of-the-Aboves).
- Rule: always ≥2 visible approaches. "Visible" includes: system defaults (attack, pick/bash/knock, swim — best to build around because internalized); deliberate leading description (chandelier on a frayed rope above the monster) — too obvious to miss without saying it. Avoid CYOA/visual-novel menu exposition.
- External Knowledge problem: don't assume players know fording, Odin/Wednesday, rafts.
- Presentation tunes Difficulty: size of the deductive leap to recognize an option = difficulty. Ideal: players realize late, then reconstruct "we should have seen it from clues X, Y, Z" — on purpose.
## 07 Scenario Design That Makes a Statement
- Pre-statement: the "for" — what need does this scenario fill (pacing between two town sessions; side trek; plot brakes). Thinks in sessions as pacing units (Town/Travel/Adventure sessions).
- Design Statement elements: Goal, Starting Point, Likely Outcomes (good/bad/indifferent, plural), Major Challenge. Any order, provisional pencil. Context often suggests where to start (villain fight → challenge given; clue encounter → outcomes first).
- Clue-encounter outcome list: gets clue / partial clue / loses access to clue / loses source, must get clue another way / false clue.
- Statement = design *assignment* (criteria & constraints), not the design. Sniff-test vs self-censor; early on aim high.
- Goal must be a finishable Win Condition, not a motivation: "explore, loot, level" → "fully explore every room and recover every valuable thing."
- Starting Point > hook: in-game circumstance that (1) reveals a goal, (2) conveys why worth pursuing, (3) points a direction to begin. Need not be explicit. Fiction plausibility: ambushed cart + smoke → bandits camped at dungeon door (deliberately unrelated to the dungeon) — psychologically makes engagement more likely.
- Best goals are both intrinsically (discovery, curiosity) and extrinsically (loot, power) rewarding.
- Outcomes: only one outcome = railroad. Not just win/lose — every reasonable way out the other end. Some scenarios can't be lost; fine. Here outcome is a completion %, players decide when done; for an optional side trek "Nope-percent" is a likely outcome. Check you can live with (keep campaign going after) every likely outcome; campaign-ending outcomes OK if intended. Don't over-enumerate unlikely ones.
- Death isn't a Lose Condition, it's Game Over. Lose conditions can't live in the engine; they're scenario-level.
- Best outcome must be the most desirable; others = settling or losing.
- Major vs Minor/Incidental challenges. Encounter: usually 1 (sometimes 2–3). Major challenge must follow *directly* from the goal, not indirectly (monster gauntlet/boss only indirectly blocks "explore everything"). Example: water dungeon — configuration of floodgates gates access to every room (Zelda dungeons). Attrition ≠ major challenge.
- Play lots of video/board games for a solution library (Dead Rising 2: clock as active enemy).
## S Interlude: Why Are We Here?
- Designers make challenges *winnable*; they partner with players; games should "feel good to lose and better to win."
- Two common adventure flavors: Maze (boxes+lines+obstacles+prize — dungeons AND flowcharts of scenes) and And Then… (situations → responses → somewhere; improv/sim/"I just create situations"). Both can be fine; every RPG needs some And Then…; advanced design elevates both.
- Quest Mindset: design every level (campaign→encounter) as discrete chunks with goal/start/outcomes/major challenge (WoW quests), even though play feels continuous and seams should stay hidden.
- "Forget the roleplaying": Pandemic could be run as an RPG with a GM. Roleplaying = veneer produced by a GM (open-ended actions, continuity, remembered consequences, narration). Good scenario is good even played by the book with no in-character speech. Design the board game first, then add what GM needs.
## 08 Win, Lose, or Draw (mostly framing)
- Q posed: OK to design an adventure players can't win? can't lose? (answered later).
- People expect games to be winnable/losable; "casual game" phrasing proves it; many secretly keep score — self-challenge is a core intrinsic motivation; no win/lose → no challenge.
- Confusion sources: system designers not grasping they make engines; off-label users (holodeck grognards, performers); RPGs are going concerns (never end); Character Death is the only engine-level thing that looks like losing, and isn't even final.
- Resolution preview: RPG play is both continuous and discrete (particle/wave, fractal); the discreteness exists precisely so win/lose can exist. Pure react-and-improvise campaigns play badly for this reason.
## 09 Quality Wins and Losses  [CORE]
- Outcomes = designed ways a scenario resolves; discrete (dragon slain / town burned; Hollow Knight endings) or spectrum (rescued count, rooms explored, treasure %). Design: build the space so player choices determine which outcome; track results.
- Outcomes needn't follow from Goals (major challenge must) — linked to the Information Gap (later).
- Win/Loss ≠ Outcomes. Win/Loss = subjective, qualitative assessments player brains assign to outcomes achieved/avoided/failed-to-avoid, usually unconsciously. Bombarded Town: best possible outcome still reads as a Loss (devastation denouement). Unwinnable scenario = valid design.
- Separate classification (W/L) from feeling (earned/deserved): a Loss can feel good if fair; a Win can feel hollow if blundered into.
- Subjective ≠ random or beyond influence. Designer is responsible for it: players know only what characters know, so their brains grab every context clue (denouement framing, NPC reactions) to score. Presentation can flip borderline cases, but has limits.
- Players constantly self-assess mid-game ("won that turn"); need periodic small-victory highs. → Quest structure / discrete chunks exist to give self-assessment, celebration, reflection points — and to give the designer a place to *tell players how to score themselves*.
- Unwinnable scenarios useful: modern D&D rarely delivers significant losses → provide needed lows; must feel earned/fair. Too many losses bum players out; want a mix of highs and lows.
- Module plan: discrete/continuous, information gap, momentum/inertia, goals vs major challenges, classifying/compounding outcomes, momentum↔major challenges, inertia↔minor challenges, roadmap.
## 10 Gaming in Fits and Starts
- Ongoing assessment ("am I winning?") drives decisions (keep doing / change it up) AND feelings (hope, pride / tension, desperation). Separate need: "am I getting anywhere?" — brains handle long delayed payoffs badly; need chunks to celebrate/reflect.
- Players never articulate this; designers don't need to think as psychologists — just structure well.
- MtG: legible position (life totals, board, hand count incl. opponent's hand *size* but not contents); Combat Phase = turn tentpole, each a mini win/loss; best-of-3; leagues/tournaments → nested incremental W/L.
- Hierarchy (deliberately vague, unimportant): Encounter, Scene (several encounters + non-encounter play; usually bounded by time/place/mode), Adventure (smallest complete scenario; defining unit), Act, Campaign, Sidequest (fits inside any chunk, non-continuous).
- What matters isn't the taxonomy but that you chunk, and that chunk boundaries aren't simply sums of encounters: major challenges exist separately from encounters; long adventures need intermediate wins bigger than an encounter.
- Quest Structure: any chunk that has Goal + Challenge + Outcomes + Context is a Quest/Scenario — i.e., impacts brains as games should. Encounters need all four too. Sidequests can span scenes/adventures if tied to one goal/challenge/outcome set.
- None of this structure should be visible to players.
## 11 What Do Players Know Anyway?  [CORE]
- "My players set goals": source of the idea doesn't matter; the designer still says "the goal of this scenario is X" and designs it. Pure reactive improv = applauding a toddler puppet show.
- Goals provide: Context (why engage; informs decisions — bribe from goblins acceptable on a chance encounter but not when goal is stopping those goblins; filler encounters feel less satisfying than goal-tied ones), Direction (which branch; which building in town), Yardstick (measure progress, score outcomes).
- Explicit vs Implicit goals. Implicit = inferred from situation; ideal for RPGs — feels organic, players feel masters of destiny. Designer ensures the inference (Choice Architecture; not "illusion of choice" — real choices, predicted).
- Tool: "Because That's How the Game Works" — genre/medium conventions predict behavior (empire attacks town → players defend town).
- No such thing as "real goal vs players' goal": Goal is by definition what players chase; the designer builds around it. The gap is Goal vs Outcomes. Goal = where players try to get; Outcomes = where they can actually get. Unwinnable = no outcome close enough to goal to feel reached; Unlosable = all outcomes close enough. Unlosable common in RPGs; both valid.
- Outcomes must still lie on the path of pursuing the goal (no Simpsons non-sequitur endings).
- Players needn't articulate or share the exact goal; vague wobbly mismatch is fine (even good) so long as aligned enough to work together and follow a designed path.
- Players won't stop chasing the goal on hitting an outcome → when an outcome is hit, the goal must be closed/done or they won't realize it's over. From the start, the goal must slide inexorably toward closure; everything players do or fail to do moves it to closure one way or the other. (→ inertia/momentum)
## 12 Inertia: Fighting Failure  [CORE]
- Inertia = a force pushing the game toward a loss (Strong) / the game's resistance to being won (Weak). All else equal, players are always losing, or at least not winning. Elastic: resistance grows the longer you play/the harder you're winning (Mario Kart rubberband).
- Play Dynamic, not Game Mechanic (like Attrition: HP/slots/rest are mechanics; the dwindling-resources feeling and press-on-vs-rest choice is the dynamic). Mechanics do many things at once — never call one "an inertia mechanic". Not physics.
- Inertia ≠ Challenge: challenges are faced and resolved; inertia can't be resolved, always present. Obstacle course + elastic band to the start (Weak; drags you back if you rest) vs Battle Royale bomb collar, getting heavier (Strong).
- Pandemic: Player Deck = resources + timer (Strong); Infection Deck vs action economy = players can barely tread water (Weak); outbreak limit + cube density → cascades grow with time (Elastic); Epidemic cards = surge + acceleration, but also localize infections (help players a bit). Lesson: in RPGs don't use fiddly cubes, but think about what inertia dynamics arise; having none is an option, kinda.
- Players bring their own inertia: boredom, frustration, time-wasting thresholds (fast-risky vs slow-safe paths). Endless adventures: players eventually abandon — bad ending note, but usable.
- System designers give few tools; D&D has very few system-level tools for advanced scenario design (macrochallenge, inertia, momentum). Attrition is no longer reliable inertia in modern D&D. Do it yourself.
## 13 Momentum: Building Victory  [CORE]
- Momentum = once players start winning they're more likely to keep winning; compounding success. Single definition. Inertia and Momentum are an antagonistic muscle pair; interplay creates the feel.
- Dynamic, not mechanic — though occasionally one mechanic *is* the dynamic (patches, timers thrown in late). Avoid; keep dynamics in mind from the start so they emerge organically.
- Momentum ≠ Progress. Clearing minions/covering miles = progress. Momentum = progress that empowers you against the *major challenge*: kobold minion carries scroll of ice knife vs the lava boss; befriending a farmer for extra food stretches rations vs delay risk. Designer's job: make progress *build* momentum.
- Pandemic: research stations (reduce wasted movement), cures make cube removal efficient. Pandemic's inertia > momentum, deliberately — balance depends on intended playfeel (always one crisis from disaster). Not 1:1.
- System tools: loot/magic items placed to arm players vs specific later challenges (4e made mid-adventure identification possible for this reason). 4e Action Points from Milestones, reset on rest → momentum + inertia → Push Your Luck dynamic (most push-your-luck = momentum vs inertia). Bennies/bonus pools are backwards (start full, dwindle). 13th Age Escalation Die = momentum + Reversal/Turnaround.
- Organic > abstract: found item that beats a later challenge (organic) vs momentum points; tiring but afraid to rest because things get worse (organic) vs turn timer.
## 14 Momentous and Inertial Adventure Design  [CORE worked example]
- Pre-design: before mapping/statting, set parameters, criteria, constraints, structure, scenes, settings, needed bits. Goal: a tug-of-war between players trying to win and the game resisting.
- Premise "End the Goblins": waterfall cave infestation; too many to kill at once; multiple sorties; win = enough violence to break them. Target: good play wins in 3–4 sessions / 3 adventuring days; bad play loses after 4–5 sessions / 5 days.
- Mere approaches: (a) static map of 15–18 encounters, cleared stays cleared; (b) roster + depletion + GM repopulates between sorties. Both fail: bailing a boat, no felt progress except counting empty rooms; difficulty flat; concentrating → players nova + dead space; dispersing → easier and duller. Want: last day ≥ first day in excitement; "how many goblins live here?!"
- Games all the way down: you never build a world/story — those are feelings to instill; any artificial means is right. Need objectivity: players win/lose by their own skill/choices. System = toolbox; invent Snakes and Ladders.
- X-Factor: the one broad activity the scenario is mostly about (Explore/Engage/Expropriate/Exterminate; go somewhere / interact / acquire / destroy…). Goal, major challenge, outcomes, momentum & inertia should all be about the x-factor. Here: Kill Something.
- "Nothing is true until the players know it; nothing is real until the players see it." Goblin population is undefined — goblins are tokens in a supply; always one more. Applies to mechanical systems, not just lore. What players see must make sense; the code underneath needn't.
- Quantum ogres = forcing a pet encounter regardless of choice = shit design. Difference: exploiting perception limits to provide fair challenges (design) vs negating choices (horseshit). Games need objectivity + agency.
- Structure: mapping = planning structure (how elements connect, how players move between them); mysteries share dungeon structures (leads instead of halls). Adventuring day 4–6 encounters ≈ one session. Three critical paths of 4–5 encounters each culminating in a major encounter; one path per sortie; side rooms/cross-cuts (red) hide structure, add exploration & luck, most groups take 4 days.
- Build inertia and momentum *separately* (easier, and creates push-pull; players see both, net decides W/L). Inertia first: imagine zero progress — how does it get worse? Here: escalation on each retreat/rest. Designer pre-builds 5 populations (visit 1 easy/random/unalert; 2 easy+avg, deliberate defense: guard posts, chokepoints, patrols; 3 normal mix; 4 avg+hard; 5+ avg/hard + 1–2 deadly). No depletion — fully restocked each visit; players read it as huge warrens reinforcing. Five one-page lists = minimal GM work.
- Momentum: x-factor is killing → killing *specific* things changes *all* future encounters (not clearing rooms): Kennelmaster dies → wolves crossed off everywhere; Warchief dies → infighting, strongest goblin crossed off every encounter; Shaman dies → cross off "god's protection" trait on every stat block. Three bosses = win.
- Balance: worst-case inertia still within system's "reasonably possible"; momentum swings in players' favor rarely ruin a good game, especially when earned. Don't sweat it.
- Design begets design: optional clever elements in side rooms — drug the bloodwine (one-visit debuff), poison mushroom room near cellar, prisoner ally/informant, secret side entrance bypassing early rooms. Keep the core systems trivially simple to run ("how many attacks so far" + "cross off thing").
- Outcomes via dynamics: raiding parties hit village each day; after 5 days villagers abandon village.
- Open problem → gamefeel: none of this counts unless players notice/feel/intuit it. What must they know vs intuit?
## 15 Challenge or Goal?  [CORE]
- Common error: writing the goal as the challenge ("main challenge: stop the ritual"). Smells: goal and challenge say the same thing; challenge expressible as a single imperative fragment. Describe in prose, don't bullet — bullets lose the "why it's hard."
- Goal = something accomplished; Challenge = something overcome. Goals speak to characters, challenges to players; goals clear/stateable by players, challenges rarely stated or explicitly understood; goals = context, challenges = gameplay; goal says how to win, challenge says what's in the way.
- Formula: "The players must accomplish X by doing Y, and Y is hard because of Z."
- Goal is mostly context (story/fantasy); the challenge is the pivot from context to gameplay — how players will interact with the game throughout. Momentum/inertia are dynamics of that interaction → stuck generating them? Your challenge is underdeveloped/confused.
- Major challenge (macrochallenge) ≠ individual challenges; even the boss isn't it — getting to the boss with enough resources is (by-the-book D&D).
- X-factor = the players' primary mode of interaction (most spotlight time, or most directly gets them the goal). The challenge should scream the x-factor. Trick: pick the x-factor first, derive the challenge.
- Open-endedness: built by layering simple scenarios fractally. Silverpine Watch: one goal (neutralize ghost), two challenges (solve murder OR gear up to destroy it), single unifying x-factor (explore).
- "Stop the ritual" four ways: Explore (find hidden site in sprawling necropolis, cover ground fast but thoroughly; time pressure from ongoing ritual); Acquire (charge a relic at holy nodes of variable yield across ruined city, then confront at skybeam); Interact (extract unwritten info from cultists — interrogation dilemmas, disguise/infiltration; civilized area limits violence; or cultists keep turning to demons); Exterminate (cut through minions with reserves for the boss; rest = gauntlet resets; need one perfect run).
## S Five Rules for Amazing Adventure Design  [CORE]
1. Game must include everything players need to play it: teach rules, teach *how to win this adventure* (each adventure has its own winning strategy — horror ≠ guns blazing), provide info for good choices. If research in town is the key, the adventure must show research is an option. Silverpine: ghost flees through locked door, key in basement side room — teaches "exploring is how you win"; side path is actually critical (contains a goal) so even a lock-bypassing rogue gets the lesson; also teaches "always a way forward for every party."
2. Action beats exposition: don't tell ("explore everything", "research first or die") — that plays the game for them; then only dice remain. Create situations where attentive players find the right choice; obviousness scales with stakes/desired difficulty. Narration word choice = difficulty slider; information management is a GM superpower. Use the critical path to guarantee the lesson lands.
3. Most natural way to play = best way to play (both: fun way is rewarded; fun way not punished). Don't build a seductive branching labyrinth then punish exploration with a brutal timer. Modern D&D players fight hostile monsters — design for it. Monsters played to win show deducible, exploitable patterns → easier to play against; "playing monsters dumb" makes it harder. If you want unnatural behavior (flee the dragon), make it the natural path, make it fun, suggest an escape strategy, without "flee or die."
4. Nothing is absolute until players see it: don't track populations; place wilderness encounters by journey stage or path choice (not quantum ogres); don't be a Skyrim save file. Also frees world-level issues (redeemable orcs, leveling world, inclusive medieval). Players only encounter parts of the world that make good gameplay; the world isn't wholly driven by gameplay.
5. Mechanical Hierarchy: No mechanics > mechanics; background > player-facing; system > scenario-specific; soft > hard. Example: don't give +1 vs Guardian per info node — stat the Guardian so certain strategies work (vulnerable to back attacks; ranged/AoE in open arena with cover) and hide clues suggesting them; players who guess right without clues still win. Plague: "A% chance someone dies each day" beats "Y die every X days."
## S Is Attrition Inertia?
- Attrition: challenges chew resources rather than end the game; makes non-lethal encounters matter and makes between-encounter choices (press on vs rest, explore side paths, sneak past, shortcuts) meaningful; plays well with boss fights. Was hard-coded into old D&D (scarce resources, wandering monsters, long recovery → avoid fights).
- Not Weak Inertia in modern D&D: retreating costs nothing — static adventures pause, monsters don't reinforce/respawn/flee, rests cheap and safe.
- Not proper Strong Inertia: pulls toward Game Over (death), not the scenario's Loss State (plague kills everyone / kills the NPC they care about).
- Fun observation: by the dynamics, modern quest-D&D "should" be deadly per encounter; old-school "should" be balanced.
- Attrition = pacing dynamic + ingredient for inertia ("unfinished inertia"): becomes inertia when hung on something — a boss that represents the major challenge; time mattering via a soft timer (each day rested, a dice toss whether someone they cared about died).
## S Open-Endedness, Open Challenges, Hat Theory  [high relevance: AI GM]
- Hats: Game Master (table, in-the-moment: describe, resolve, pace, engage), Campaign Manager (next session exists: logistics, conflicts, policies), Scenario Designer (goals, challenges, progressions — top-down, slow, "part artist part clockmaker"). Never wear two at once. GM can't design under per-action time pressure; SD can't run.
- SD's job: make sure GM never has to make anything up → predict player choices (if X, Y, or Z, prep those three).
- Improvisation ≠ scenario design; it's a GM tool to keep the game moving (move a fight earlier, sudden hook, clue to unstick) — not a long-term strategy. Off the rails → GM handles in session (steer back / improvise to end / stop early) → after session reports to SD, who builds the next piece.
- Open-endedness comes from the GM adjudicating, not from the scenario; a script doesn't reduce it. A scenario = "if players do X, here's what you need" + state of the world ("wall here"; "terrorist holds hostage, gun to head"). Good scenarios motivate designed choices + include contingencies (if sneak / talk / fight).
- So SD needn't sweat open-endedness; the bigger problem is a game playable *without* player creativity.
- MacGuyver solutions = inspiration flashes (luck, sensory input, familiarity with objects/skills); slot machine. Players don't really know what their abstract skills can do. Design tests of *reason/deduction*: make sure a reasonable player notices the valise is missing and searches; tune so inexperienced players very likely find the vital clue but only skilled players find the optional edge-giving clue. Target: failure that elicits "I totally should have realized that; I deserved to lose."
- "I don't build encounters, I build situations" is not a flex.
## 16 Struction: Intro to Structure
- Three design approaches: Top-down (big picture — goals, macrochallenges, dynamics — then chunk and build to plan) → "remember that awesome adventure where…"; Bottom-up (build encounters/map and string/populate) → "remember that awesome encounter?"; And-then (iterative, each next thing follows from current — improv GMs *and generative AI*) → "remember when I did that thing?"; least cohesive, most shallow. [OUR GAME: explicit warning about LLM-as-GM default mode.]
- Structure = deliberate relationship among elements; dungeon map is a diegetic flowchart.
- Two structures: gameplay (how players navigate challenges, how victories/defeats carry forward) and narrative (rising action, climax, acts). Gameplay structure dominates in-play feel; narrative affects post-play memory and still matters (narrative is a gameplay aesthetic). Cake vs Spongepants decoration: must taste good first.
- Tension: best narrative quest structure = three acts; best gameplay structure (esp. open-ended) = four-part progression; the four parts fit inside act two with acts one and three as bookends; not every progression needs all four.
- Story quality depends on telling, not subject; good storygames help bad storytellers tell well.
- Gameplay structure elements: Shape (linear/branching/looping/open; nested; mix), Flow (how engagement changes event to event — player-driven investigative vs tight urgent ambush; broader than "mode"), Progression (how gameplay builds: players gain skill/resources, game escalates to demand them). Silverpine: 4 zombies in a controllable divided arena → 5 in a cluttered arena; zombies revive unless fire/holy → later blacksmith regenerates unless fire/holy; corpse teaches interacting with scene → desk with clues for right questions → bonus treasure for thorough search.
- Stand back and squint: shape/x-factor judged by felt impression, not counting encounters.
- Narrative mirrors gameplay: arcs ↔ progression, act shape ↔ shape, pacing ↔ flow. Map plot points → scenes/encounters; story arc along critical path; sidequest holds an NPC's character arc; final challenge = climax.
## 17 Structure All the Way Down  [CORE]
- Scenarios are made of scenarios: campaign ⊃ arcs ⊃ adventures ⊃ scenes ⊃ encounters. Adventure = baseline "medium size"; purest complete playable form. Arcs and scenes are optional intermediate layers but not mere containers — skipping or including them changes playfeel.
- Design intent matters (adventure paths are campaigns, not arcs).
- Top-down: design the LEGO set, then the bricks.
- Every part (scene, encounter) has goal, outcomes, challenge, dynamics (with size modifiers). Encounters have shapes: pure combat = linear; fight-or-sneak = branching; poke-around room / crime scene = open. Encounters have x-factors too; a combat encounter can be an investigation or exploration scenario.
- Macrochallenges & dynamics arise from how part-outcomes feed into each other and the whole.
- Outcome Gating: for scenes/encounters you must know how the adventure continues after *every* possible outcome. A part whose outcome can end the adventure is an outcome gate. Valid and necessary — a losable adventure must have points where victory becomes impossible; usually several. Only-fail-at-climax = single-encounter adventure with a long meaningless prologue. Success depends on surrounding design, not rules like "can't fail before act 3" (one real hard rule — unstated, later).
- Death isn't an outcome (Game Over). "Don't die" is a system-level goal competing with scenario goals; designers don't build it into outcomes. A must-win combat to advance is, to the designer, a can't-lose scenario.
- Example "Yellow-Orange Sigil": 3 linear scenes. Town (open shape; can't-lose; variable outcomes = how equipped + what you risk/pay): research for info/resources + choose between (or both) mad hunter guide (capable in forest, trigger-happy, may turn) vs grave-robbed journal (preparation & poison warnings, but curse + reading side effects). Forest (linear gauntlet of hazards; can't fail; setbacks chew resources; hunter helps/risks). Hut (branching/labyrinthine; hazards, puzzles, poisons, plant monsters; sigil behind navigation puzzle / tablet clues; failure possible: madness timer — take too long → wake naked outside town, scars; return finds collapsed ruin, sigil lost). Squint: overall shape labyrinthine (dungeon dominates time and memory); x-factor mystery/investigation/exploration. Memories: the hunter, the journal, solving a puzzle while senses lie — not the plant fights.
## S When Is a Scenario Not a Scenario?
- The "lie": not everything is a Scenario. Lots of small-e encounters (exposition meeting with burgher, harmless roadside traveler, world-flavor nobody, pop-culture gag) have no goal/challenge — like unlabeled houses on a town map or empty dungeon rooms. Entrance-hall analogy: the quest-giver meeting is the dungeon threshold — pacing + promise. Denouements can't be scenario elements by definition.
- Big-E Encounter = encounter with goal + central challenge + prescribed outcomes; distinction only matters in the designer's context (tomato is a vegetable *in the kitchen*). GMs just run what's written.
- Published modules hide the frame (house framing under drywall). Silverpine = 4 parts: Incitement, scene, Scene, Denouement.
- Shapes referenced: Hub-and-Spoke, Open, Labyrinth, linear, branching (a shape lesson exists — "The Shape of a Scenario" — listed "coming soon" on index; not read).
- Why the lie: to make you see space for gameplay at every level — can players start winning or losing the adventure before they leave town?

# Let's Build a Pretty Good Dungeon (series)
## D1 Introduction
- Three principles: (1) path of least resistance must lead to the best experience; (2) players can't choose to ruin the experience (may deviate; deviation can make things harder, never an unplayable screwjob); (3) respect the system (D&D's 4–6 encounter resource-management assumption; deviating requires compensation).
- Order matters: empowerment, fairness, pacing (tension oscillates, rises overall), narrative (context before conflict). Order is a non-mechanical difficulty knob: lock-before-key is easier than key-before-lock.
- Agency the designer cares about: freedom to explore on own initiative (primary engagement in a delve); open-ended creativity is the GM's job.
- Premise "Reclaim the Place": three infestations in three wings; each cleared only by a specific task (free restless spirit stops undead; collapse tunnel to Underdark). Players aren't told the structure; "they only have to know enough to start and figure out enough to win." Partial clears → partial refund = element of challenge.
## D2 Critical Paths
- Pathing applies to any scenario (dungeon, mystery flowchart, open world).
- Critical path = minimum required route through every must-do. Golden path = optimized route for best feel; contains the critical path, may wander (Entrance–Puzzle–Poem–Puzzle: see lock before key; sidetracking/backtracking give agency; "the path forward is sometimes behind you"); includes narrative context (mystery backstory).
- Required (critical) / Expected (golden: skipping it makes play frustrating, incomplete understanding, or hollow victory) / Optional (no significant loss). Designer decides category and then makes it so — icebrand vs fire dragon: required → near-impossible without; expected → balanced assuming you have it; optional → balanced without it, easier with.
- Optional content appeals unevenly, costs time/resources; diminishing returns; too much drowns the meal. Its *presence* matters more than its effect (next).
- Forked golden paths (assault vs infiltrate; order-free three ingredients): chunk and give each its own golden path; both branches must be equally good. Bottlenecking re-merges paths.
- Golden path ≠ only path. Goal: golden path = path of least resistance (the one players most likely follow) while leaving a couple of alternatives.
## D3 Exploring Spaces
- Explorable space = qualitative size of the "what now?" list the players hold *at this moment* — includes routes from here, every untaken earlier route, and newly-unblocked routes; as players parse it (road / forest / caravan), not physical reality. Applies to mysteries, flowcharts, open worlds.
- Existence matters more than size; too big is a failure. If players can't hold options in their heads, the options don't exist (consulting a map for 12 doors = chores). Hand rule: ~2 small-satisfying, ~3 moderate, 4 (briefly 5) large. Not math.
- Options must be distinct and differentiated; nondescript doors → players open every one hunting for something to be curious about. Few clear options > many vague ones.
- Exploration isn't an activity; it's a motive — satisfying curiosity by asking a question and seeking the answer. Wandering must keep resolving into new questions or the drive dies.
- Explorable space is really about navigation; exploration is one motive among others.
- The core method: draw space → identify golden path → turn players loose → ensure the *most attractive* item on the players' current checklist is always the next golden-path step; and no other item leads to suck. "Path of least resistance" = the path players behaving like players are most likely to choose. Requires knowing what makes options attractive and memorable and how players decide given goals, mood, preferences, gamestate.
## D4 How Players Explore  [CORE — navigation psychology]
- Disclaimer: heuristics; conscious brain rationalizes after the fact; behavior broadly predictable across players; descriptive, not deterministic, not deceptive (helping them spot choices they want). Unreliable → hence "no choice may lead to suck." "My players are different" usually means you're short-circuiting them.
- "What next" list includes: visible exits, untaken earlier paths, grayed-out options (unsolved puzzle, blocked obstacle), abstract actions (rest, re-search storeroom).
- Directional decisions between identical options are the worst: brains insist every choice has an optimal answer and hunt for any differentiator → endless arguments. Players want *action* decisions with direction attached: Chase monster (N, forward) / Sparkly river (E, sideways) / Puzzle (backward) / Gate (backward) / Rest (backward). Players constantly label forward/sideways/backward — relative to the *current* goal (which may be "find safety"). Scuffed floor vs rusty door = forward vs sideways.
- Two modes: Seeking (toward a current goal, efficiency; strong — will glom onto anything path-like, e.g. follow a river); Exploring (see everything, FOMO; forward is the "wrong" way). Most groups default to Exploring, return to it after finishing something; but brains hate exploring as non-progress → they explore looking for a non-primary goal to Seek, Seek it, repeat. Hyperexplorers/hyperseekers are rare and tempered by the group.
- Design implication: invite exploration and scatter progress indicators, or demand focused progress with regular short rewarding diversions (Guided Nonlinearity / Closed Open Worlds).
- Seeking triggered by urgency, efficiency benefit, emergency (collapse the entrance → seek exit first). Too long in Seeking → stress as untaken paths pile up; too long in Exploring with no goal worth seeking → lost, listless; must feel the space is shrinking.
- Completion Bias: once a path/goal is chosen, they want to finish it; won't re-decide at minor forks (stay in red tunnel past grey fork). Breakers: let them finish; show a more interesting/useful/urgent thing; block them (but they hate backtracking — will try to chew through the gate); recontextualization (key for the old door, rune matches dead-end wall) — weaker than Metroidvania fans think, pair it with something; the Door to Before (loop that drops you back near the recontextualized obstacle) = three-hit combo.
- Threshold Effect: at major transitions ("before we move on, shouldn't we…") players re-examine the list; doesn't force a turn back.
- Tiebreakers when equal, in power order: Exigency (will expire: chase Hornet) > Recency/Availability (nearest, most recently learned/reminded) > Unclosed Loop (unfinished business) > Salience/Memorability (unique, sexy, visible reward behind gate). Designers can reweight (frustration boosts unclosed loop) and stack (salient + nearby + new).
- Make directions look different, even just red vs grey.
## D5 Checkpointing
- Checkpoint = deliberate designer-created opportunity to rest, bank progress (not retread ground after retreat/emergency), or detour. Gives "you got this far" hits; tension release; space for maintenance/side business.
- Players resting anywhere in hostile territory = bad gameplay; resting in a dungeon should be a desperate last resort. Without designer checkpoints, players compulsively rest constantly (when resting is safe) or never (when it means backtracking — completion bias + hatred of going backward → death spiral; the deeper you go the less you'll stop). Neither is a real strategic choice — resisting compulsion is willpower, not challenge. Resting after the system's expected 5 encounters should never feel bad.
- Spacing = gamefeel dial: far apart → push harder, checkpoints feel rewarding, more challenge; close → less demanding, players nova and feel badass. Players learn the rhythm; starvation = stress.
- Opportunity ≠ coercion: momentum players push past ("mark it on the map"); checkpoints make retreat more likely (only back to the last one); players learn to seek them sideways when drained.
- Map as paths & path segments, not as architecture. Depth = number of costly/risky challenges between one major navigational decision (or checkpoint) and the next. Ensure no rational path demands more depth than the system tolerates before a checkpoint or a forced turnaround (guard room always manned = 1; each wing then 3–4 to its end).
- Types (functions, not constructs): Safe Space (must *scream* safety via salience — hidden shrine behind waterfall; weakest: rest only); Shortcut (one-way-unlockable link back to earlier space — barred door, mechanism gate, rope from above, secret door visible from behind; Dark Souls ladder/elevator, Bloodborne); Side Door (new exit/entrance found from inside; hidden cave mouths — don't hand players ten indistinguishable entrances); Fast Travel (teleport circle linked to a return gate; elven tree-fort lowerable lifts).
- The art = meeting mechanical criteria while making it feel like a thing in the world.
## D6 Let's Map a Pretty Good Dungeon (blockout)
- Site-based scenario: the map is the plot (structure = layout). Dungeons best for learning.
- By mapping time you already know what the map must be (goals, system constraints, navigation psychology).
- End the Goblins needs: 3 paths × 4–6 encounter spaces, each ending in a miniboss and facilitating retreat/rest, looking like a goblin warren → "obscuring the path."
- Blockout = rough blocks sized/positioned for gameplay chunks (flowchart + rough geography); quick, playful, paper/pencil or sketch layer. Interconnection (central multi-storey chamber crossed by bridges/balconies) orients players, makes linear feel open, enables lowerable ladders/elevators as shortcuts.
- Blocks are games, not rooms: one block may span several rooms (catacomb skeleton ambush, minotaur labyrinth, three-room library). Count blocks against 4–6 rule; ≥25 squares per action block; never >6 blocks in a row without a stop-and-think trick (dead end, door to before, alternate exit, checkpoint, goal, threshold).
- Two steps: (1) block sections along the golden path, each 4–6 blocks ending in something checkpointy/goal-completing. Blue: warchief then dead end → forced back to entrance → natural rest. Red: kennelmaster then path continues to hidden surface backdoor → players push on, then rest outside. Green: shaman then one-way door-to-before; finding it from the wrong side = harmless sequence break. (2) Hide the path: add optional side rooms, a branch, and cuts between sections until the plot is hard to spot unlabeled. Not every block holds a risky encounter. Careful with cuts: forward-biased players shouldn't be dumped from the end of a full day into the middle of another.
- Then draw any map over it; gaps needn't be walls (impassable river with bridges, one retracted = shortcut). Encounter features (terrain, pools, columns) = encounter design, a later step.
- Remapping realistic floor plans: real buildings are too open (built for people to reach anything easily — "the opposite of an adventure"); goal-seekers go straight to the sanctuary. Overlay a golden-path blockout, then edit: move/remove/lock/bar doors, rubble, collapse rooms, breaches; flood, mud, growth, lava, fumes, voids. Abbey: enter via gatehouse or narthex breach → forced courtyard (gargoyles) → dormitories branch (interior rooms vs poisoned cloister garden) → sanctuary boss from the west; workrooms optional.
